# Experiment log

What happened during the campaign that a reader of the results should know. Times are UTC, from the
container clock.

| When | Event | Effect on the data |
|---|---|---|
| before the campaign | Smoke runs with `--rep 0`: `db-failure` (final), `data-loss` (final, twice). The first `data-loss` smoke run restored the newest backup, which had been taken 11 s **after** the records were destroyed, so the restore brought back nothing (0 of 1 220 payments). The restore tool got a `--before <time>` option and the scenario now passes the time of the loss | Smoke runs are deleted and are not in the results. The finding is discussed in REPORT.md §10.4 |
| final, repetition 1, `high-load` | **Operator error by the experimenter.** The integration test suite (`pytest tests`, which includes a test that stops the database primary) was started by mistake against the stack while the run was being measured. The run recorded a database failover that the scenario does not inject | The run was discarded (results and raw log deleted) and repeated after the rest of the final campaign, with `npm run campaign -- --reps 3 --resume`. No other run overlapped with the test suite: `txn-interrupt` r1 had finished 90 s earlier and `gateway-failure` r1 started its known-state restore after the suite had ended |
| baseline, first campaign (17 runs) | Stopped at the first submission deadline with every scenario run once and four run twice. In all of them `BackupStale` fired from start to end: the controller exported `backup_last_success_timestamp_seconds` as 0 where no backup exists (an unlabelled Prometheus gauge is 0 from the moment it is created) | **All 17 runs were discarded** and the baseline campaign was repeated in full after the fix (the gauge is now created on the first backup seen). The request, latency and integrity figures of the discarded runs agree with the repeated ones; they are not in the results |
| after the first baseline campaign | The fix above changes only that gauge. The final campaign had been measured with the earlier image; in final a backup exists within 15 s of start, so the gauge held a real value in every final run and the fix does not affect them | none: the final runs were not repeated |
| integration tests | 3 of 22 failed on their first run against the final stack. Two connected to `postgres-primary` as "the primary" after a failover had swapped the roles; one re-sent payments while the payment circuit breaker was still open after the promotion | The tests were corrected (they ask the controller which node is the writer, and retry a 503 for up to 15 s). 22 of 22 pass, twice in a row, with the roles in both orders (`integration-final.txt`) |
